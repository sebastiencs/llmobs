# B2 · Official GenAI and OpenInference (K11–K13)

See [README.md](README.md). From here on, each sub-phase adds scenarios and captures with the harness from K2–K10. The rules below apply to K11–K20.

## Common rules for capture sub-phases

- **Edit only:**
  - `tools/capture/{py,ts}/**`: scenarios, the project's dependencies and lockfile, and the harness module only to fix a bug;
  - `fixtures/otlp/<group>/<case>/{case.json,input.json}` for the cases the sub-phase lists;
  - `tools/capture/src/**` only for a bug fix or a new wire detail the clients need, with tests, listed in the report.
- **Before writing a scenario, read the instrumentation's installed source** (in `.venv` or `node_modules`):
  - how it's enabled;
  - which switch makes it record message content **on spans** (not as log events);
  - which attributes it writes.

  Put content switches in the scenario's `env`, never in `main.py`. If an instrumentation can only put content in OTel log events, capture it as it is, say so in `notes`, and report it: spec 02 doesn't ingest logs.
- **One scenario per case.**
  - Content is synthetic and short.
  - The model names must have a row in `fixtures/otlp/prices.json`. If one doesn't, report it to B1 rather than editing the file.
  - Embedding scenarios use `dims` ≤ 8.
  - A multimodal scenario uses a tiny synthetic image, a 64×64 PNG generated by the program, not a file from the internet. Set `settings.media_min_bytes` below its size so B1 can exercise media extraction.
- **Streaming scenarios:**
  - request usage in the stream where the API allows it (`stream_options={"include_usage": True}` for OpenAI Chat);
  - set `ttft_ms` to 120 and `chunks` to 4, so TTFT is visible in the spans;
  - list every measured timing attribute you find in `timing_attributes`.
- **`description`** says what is exercised. **`notes`** records:
  - the content-capture switches;
  - any behaviour that surprised you;
  - "Covers D111 (…)" when the case pins one of B1's single-source behaviours.
- **After each capture:**
  - run `just fixtures-check`;
  - recapture with `just check-capture`;
  - read the `input.json`.
- **Report, per case:**
  - the attributes spec 02 doesn't know;
  - the spec rows the capture contradicts;
  - the token semantics observed: did the instrumentation copy the provider's numbers as they are, or convert them? Compare with the scenario's scripted OTel-semantics usage.

  B1 decides what to do with each (R2). **Don't edit specs here.**
- **Dependencies:** the newest release older than 7 days, exact pins, `uv lock` / `pnpm install`. One instrumentation package's requirements may force a different version of a shared package (`openai`, `opentelemetry-sdk`). Pick a version that satisfies all of them and report it. If none exists, report that too, and don't split the project.

## K11 — Official OTel GenAI instrumentations

**Commit:** `capture: record the official OTel GenAI instrumentations`

**Packages** (latest on 2026-11-10, for orientation): `opentelemetry-instrumentation-openai-v2` 2.4b0, `opentelemetry-instrumentation-google-genai` 1.3b0, `google-genai` 3.1.0.

**Switches:** these instrumentations record content only when asked, and the attribute-based form (`gen_ai.input.messages`, `gen_ai.output.messages`) may need the latest experimental semantic conventions to be opted into. Find the variables in their source, typically `OTEL_INSTRUMENTATION_GENAI_CAPTURE_MESSAGE_CONTENT` and `OTEL_SEMCONV_STABILITY_OPT_IN=gen_ai_latest_experimental`. Choose the mode that puts content **on spans**, and record it in `env` and `notes`.

**Cases** (group `genai`):

| Case | Scenario |
|---|---|
| `openai-v2-chat-tool` | The K10 conversation (tool call, then answer) through `opentelemetry-instrumentation-openai-v2`. |
| `openai-v2-chat-stream` | One streamed chat answer with `include_usage`. |
| `openai-v2-embeddings` | One embeddings call with two inputs, `dims` 8. Skip it, and report why, if the instrumentation doesn't trace embeddings. |
| `google-genai-multimodal` | `generate_content` with a text part and the synthetic PNG as inline data, answered with text; usage includes `cache_read`. Through `opentelemetry-instrumentation-google-genai`, with `google-genai`'s client pointed at the mock (`http_options.base_url`). |
| `google-genai-stream` | One `generate_content_stream` call whose answer has a reasoning part (`reasoning` usage > 0), so `thoughtsTokenCount` appears. |

## K13 — OpenInference frameworks

**Commit:** `capture: record OpenInference framework instrumentations`

**Packages** (2026-11-10):
- `openinference-instrumentation-langchain` 0.1.82;
- `openinference-instrumentation-openai-agents` 2.7.1;
- `langchain` 1.4.10, `langchain-openai` 1.7.4, `langgraph` 1.2.20;
- `openai-agents` 0.24.0.

Each framework calls OpenAI through the mock. Only the framework instrumentation is enabled, not `openinference-instrumentation-openai`, because that is how these are usually installed. That gives one convention per case. If the framework's documentation recommends enabling both, add a second case with both enabled and say so.

**Cases** (group `openinference`):

| Case | Scenario |
|---|---|
| `langchain-chat-tool` | `ChatOpenAI` with one bound tool (`@tool get_weather`): a model call that returns a tool call, the tool run by LangChain, a second model call. This should give chain, LLM and tool spans. |
| `langgraph-agent` | The current prebuilt ReAct-style agent (check the LangGraph/LangChain 1.x API: `langchain.agents.create_agent`, or whatever replaced `create_react_agent`) with the same tool and two model turns. |
| `openai-agents-tool` | An `Agent` with one `@function_tool`, run with `Runner.run_sync`. It talks to the Responses API, so turns are `openai.responses`. Disable the SDK's own tracing export to OpenAI (`set_tracing_disabled` or its equivalent; check the SDK) so it makes no network call outside the mock. |

The captures may hold more spans than the turns suggest (graph nodes, agent and handoff spans). That's the point: keep them all. If one capture exceeds 256 KiB, reduce the prompt sizes, not the steps.
